**1. #12174 lock-scope fix (rdpei_main.c, the ONLY permitted channel edit per D-06/CONTEXT.md)**

In `rdpei_touch_process` (channels/rdpei/client/rdpei_main.c, starting line 1052):
- REMOVE the `LeaveCriticalSection(&rdpei->lock);` at line 1069 (immediately after `contactPoint = rdpei_contact(...)` and the `contactIdlocal` assignment).
- ADD `LeaveCriticalSection(&rdpei->lock);` after the `if (contactIdlocal >= 0) { ... }` block that calls `context->AddContact`, specifically before the `if (contactId) *contactId = (INT32)contactIdlocal;` assignment at ~line 1127.
- This widens the locked region to cover both reserve (line 1066) and publish (line 1124). WinPR CriticalSection is recursive (critical.c:189-194), so `rdpei_add_contact`'s `EnterCriticalSection` at line 1042 will recurse (RecursionCount++) rather than deadlock. The poll thread cannot run `rdpei_add_frame` during the publish because it needs the same lock.
- Do NOT change any other line in rdpei_main.c. This is the only channel edit.

**2. xfContext touch-lifecycle state fields (xfreerdp.h)**

**3. XI2 touch ownership + emulated-pointer suppression (xf_input.c)**

3a. In `register_input_events` (xf_input.c, the `XITouchClass` case, lines 108-123): after the three existing `XISetMask` calls for `XI_TouchBegin`, `XI_TouchUpdate`, `XI_TouchEnd` (line 119-121), add one line: `XISetMask(masks[nmasks], XI_TouchOwnership);`. This selects the ownership event so the client can accept touch grabs.

3b. In `xf_input_handle_event_remote` (xf_input.c, lines 853-904): add a new `case XI_TouchOwnership:` in the switch. On `XI_TouchOwnership`, extract `deviceid` and `touchid` from the `XIDeviceEvent*` (cookie->data): `deviceid = ((XIDeviceEvent*)cookie.cc->data)->deviceid`, `touchid = ((XIDeviceEvent*)cookie.cc->data)->detail`. Call `XIAllowTouchEvents(xfc->display, deviceid, touchid, xfc->window->handle, XIAcceptTouch)`. Then fall through to `xf_input_touch_remote` (same as TouchBegin/Update/End do). The accept-on-begin model is the exclusive model appropriate for a fullscreen RDP session per D-09.

3c. In the `XI_ButtonPress` / `XI_Motion` / `XI_ButtonRelease` branch (xf_input.c, lines 875-892): before the pen check, test whether the event is emulated from touch. The `XIDeviceEvent` has a `flags` field. Use `XIMaskIsSet(deviceEvent->flags, XIPointerEmulated)` (or test the `XIPointerEmulated` bit on `deviceEvent->flags`). When the event IS emulated from touch, `break` out of the switch without calling `xf_input_event` — the touch path already handles the real input. When NOT emulated (genuine mouse/stylus), fall through to the existing pen check and `xf_input_event` as before. This suppresses only touch-generated pointer duplicates while preserving real mouse and stylus input (Pitfall A from RESEARCH.md).

**4. Content-bounds gate (D-11) in xf_input_touch_remote (xf_input.c, lines 641-673)**

Before the `xf_event_adjust_coordinates(xfc, &x, &y)` call (line 655), add a content-bounds check on the RAW window coordinates (`event->event_x`, `event->event_y`):
- Compute the content rectangle: left = `xfc->offset_x`, top = `xfc->offset_y`, right = `xfc->offset_x + xfc->scaledWidth`, bottom = `xfc->offset_y + xfc->scaledHeight`.
- If `event->event_x < left || event->event_x >= right || event->event_y < top || event->event_y >= bottom`, return 0 without forwarding (no RDPEI contact, no pointer motion). This replaces the current `CLAMP_COORDINATES` behavior (which silently floors negatives to 0) with explicit ignore per D-11.
- This check must run BEFORE `xf_event_adjust_coordinates` because the transform subtracts `offset_x/offset_y`, which would mask the letterbox condition.
- The fields `offset_x`, `offset_y`, `scaledWidth`, `scaledHeight` are already maintained by `xf_event_ConfigureNotify` (xf_event.c:840-866) and are available on `xfc`.

Do NOT add the fallback latch, forced-cancel, recovery gate, or idempotency logic — those are Plan 2. This tracer only needs the four fixes above plus the existing `xf_input_touch_remote -> freerdp_client_handle_touch` path (which already works per the #9082-absent verdict).
