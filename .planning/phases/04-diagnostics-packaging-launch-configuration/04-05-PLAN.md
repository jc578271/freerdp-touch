Fix three independent script/menu defects. Each file is separate; no cross-file dependency.

**GAP-05 (shell) — Oversized calibration bypasses validation (BL-05 shell half):**
In `scripts/launch-touch.sh`, the calibration validation currently does: digits-only case check, then `[ "$lp_raw" -lt 500 ] || [ "$lp_raw" -gt 700 ]`. For a very long digit-only value (e.g., 84 digits), the `[ "$val" -lt ... ]` comparison produces an "integer expression expected" error (non-zero exit from `[`), but because both sides of the `||` fail, the `if` condition is false and the script continues to invoke FreeRDP with the oversized value.

Fix: Add a length guard BEFORE the arithmetic comparison, for both FREERDP_TOUCH_LONG_PRESS_MS and FREERDP_TOUCH_SLOP_PX. After the existing digits-only `case` check passes and BEFORE the `[ "$val" -lt ... ]` comparison, add:
```
if [ "${#val}" -gt 10 ]; then
    echo "ERROR: <VARNAME> is too long (max 10 digits), got '${#val}' digits" >&2
    exit 1
fi
```
10 digits covers up to 9,999,999,999 which is far beyond any ms/px value (500-700 ms, 4-16 px). This rejects overlong values before they reach shell arithmetic. Also add a noncanonical check: reject multi-digit values with leading zeros (e.g., "0600") since those are noncanonical decimal. After the digits-only check and before the length check, add:
```
case "$val" in
    0[0-9]*) echo "ERROR: <VARNAME> must not have leading zeros, got '$val'" >&2; exit 1 ;;
esac
```
This rejects "0600" but allows "0" alone (though "0" would fail the range check anyway). Apply the same pattern to both FREERDP_TOUCH_LONG_PRESS_MS and FREERDP_TOUCH_SLOP_PX. Keep the existing digits-only and range checks after the new guards.

**GAP-06 — Interrupted release build exits successfully (BL-06):**
In `scripts/build-release.sh`, the single `trap cleanup EXIT INT HUP TERM` (line 63) causes two problems: (1) a signal arriving while waiting for a child can enter cleanup with `$? == 0`, making the interruption appear successful; (2) the signal trap runs cleanup, then `exit $rc` triggers the EXIT trap which runs cleanup again (double cleanup).

Fix:
1. Change the trap registration from `trap cleanup EXIT INT HUP TERM` to `trap cleanup EXIT` only. The EXIT trap fires once on any exit (normal or signal-triggered) and captures the correct `$?`.
2. Add separate signal handlers that set the correct exit code without calling cleanup directly:
```
trap 'exit 130' INT    # 128 + 2 (SIGINT)
trap 'exit 129' HUP   # 128 + 1 (SIGHUP)
trap 'exit 143' TERM  # 128 + 15 (SIGTERM)
```
When a signal arrives, its handler calls `exit <128+signal>`. This triggers the EXIT trap, which runs `cleanup` once with `rc=$?` set to the 128+signal value. The cleanup function captures `local rc=$?` (which is now 130/129/143, not 0), does its publication-aware cleanup, and calls `exit $rc`. This fixes both the wrong exit code and the double-cleanup. The publication-aware guard in cleanup (comparing `readlink -f dist` to `bundle_dir`) already preserves the prior valid bundle when the swap has not completed.

**GAP-08 — README checksum instructions break the following install command (BL-08):**
The current checksum verification command is:
```
cd "$(readlink -f dist)" && sha256sum -c SHA256SUMS
```
This leaves the caller's working directory inside the resolved bundle directory. The next documented command references `./dist/...` which now resolves to a nonexistent path inside the bundle.

Fix: Wrap the checksum verification in a subshell so the caller's working directory is unchanged:
```
(cd "$(readlink -f dist)" && sha256sum -c SHA256SUMS)
```
The parentheses create a subshell; the `cd` affects only the subshell. After the subshell exits, the caller is back at the repository root and the following `./dist/...` install command resolves correctly. Do not change the install command itself — it already uses `./dist/...` which is correct from the repository root.

**GAP-09 — README rollback assertion fails open (BL-09):**
The current rollback assertion is:
```
dpkg-query -W -f='${Version}\n' \
  freerdp3-x11 libfreerdp-client3-3 libfreerdp3-3 libwinpr3-3 \
  | grep -q '+onemix1' && echo "STILL PATCHED -- retry trixie closure" \
  || echo "ALL STOCK -- safe to launch"
```
If `dpkg-query` fails because a package is missing (e.g., the closure is broken), grep sees no `+onemix1` text and the `||` branch prints "ALL STOCK -- safe to launch" — declaring a broken closure safe.

Fix: Replace the pipeline with a fail-closed assertion that requires exactly four successful dpkg-query results before checking versions. Use a structure like:
```
versions=$(dpkg-query -W -f='${Package} ${Version}\n' \
  freerdp3-x11 libfreerdp-client3-3 libfreerdp3-3 libwinpr3-3 2>/dev/null)
if [ "$(printf '%s\n' "$versions" | wc -l)" -ne 4 ]; then
  echo "INCOMPLETE CLOSURE -- unsafe to launch"
else
  printf '%s\n' "$versions" | grep -q '+onemix1' \
    && echo "STILL PATCHED -- retry trixie closure" \
    || echo "ALL STOCK -- safe to launch"
fi
```
This requires: (1) dpkg-query succeeds (captures output; if it fails, `$versions` is empty), (2) exactly four lines are returned (one per package; a missing package returns no line), (3) only then does it check for +onemix1. If fewer than four lines are returned, it prints "INCOMPLETE CLOSURE -- unsafe to launch" and does not declare safe. This fails closed for missing/broken closures. Use the exact package names from the existing README (freerdp3-x11, libfreerdp-client3-3, libfreerdp3-3, libwinpr3-3).

After editing, verify the README contains the subshell checksum pattern and the fail-closed rollback assertion with the "INCOMPLETE CLOSURE" or equivalent unsafe message.
